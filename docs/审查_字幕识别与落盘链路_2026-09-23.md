# 字幕识别与落盘链路 —— 代码审查报告

> 审查日期：2026-09-23
> 审查方式：纯静态代码分析（未启动任何实例）
> 审查版本：v0.10.3（HEAD: 20e66a9, 分支 cline/7c62c）
> 审查动因：用户反馈"字幕识别疑似在后台不落盘"

---

## 0. 一句话结论

**后台录音/识别/落盘链路本身是通的**（前台服务声明正确、写盘全在服务内、不依赖 UI）；但发现三个真实 bug 会造成"字幕没落上/没识别"的观感或事实：

- **【严重】保守分句模式下，精修字幕整段静默不落盘**（与前后台无关，纯逻辑缺陷，§2.1）；
- **【严重】同一次 App 会话内"停止→开始"后复用"死"离线引擎，整场无流式识别**（§6.1-#12）；
- **【中】退后台期间 UI 字幕断层**（CaptionBuffer 挂在 Fragment 生命周期上，后台事件被丢弃，§2.2）。

另有若干收尾竞态、安全面、一致性问题，见 §3；第二轮全量审查（含记录页/设置页/AI 链路/构建配置）见 §6。

## 1. 后台落盘链路验证（结论：正常）

| 检查项 | 结论 | 依据 |
|---|---|---|
| 前台服务声明 | ✅ 正确 | `AndroidManifest.xml:27-30`：`foregroundServiceType="microphone"` + `FOREGROUND_SERVICE_MICROPHONE` 权限 |
| 启动方式 | ✅ 合规 | `ListenFragment.kt:194` 前台界面 `startForegroundService` 启动，满足 Android 12+ 后台麦克风限制 |
| 转录写盘位置 | ✅ 服务内 | `RecorderService.kt:179-186` `commitSentence()` → `transcriptFile.appendText()`，完全不依赖 UI |
| WAV 落盘 | ✅ 服务内录音线程 | `RecorderService.kt:605-627` `processChunk()` 直接写 RandomAccessFile |
| 广播无人接收的影响 | 仅影响 UI | `MainActivity.kt:53` `listenSink?.invoke` 空转不影响文件写入 |

**即：原生 Android 上，退后台后录音、识别、转录写盘均继续工作。** "退后台即停止落盘"不成立。

> 例外（环境性、非代码 bug）：国产 ROM（vivo/OPPO/小米）省电策略可能直接杀进程，进程死则服务亡。建议引导用户加电池白名单；必要时持 partial WakeLock。见 §3-#11。

## 2. 两个核心 bug（直接对应用户感知）

### 2.1【严重】保守分句模式下，精修字幕整段静默不落盘

**现象**：字幕正常显示，但转录文件里只有头尾标记和一段无标点流式残句，精修内容全部丢失。

**根因链**：

1. `transcriptFile` **只在 `commitSentence()` 里惰性创建**（`RecorderService.kt:182` → `openTranscriptFile()`）。
2. 保守模式（v0.10.3 主推的"纯精修链路"）下，流式 zipformer 输出**无标点**：
   - `SentenceSplitter.mergeConservative()`（`SentenceSplitter.kt:145-165`）只在句末标点定稿 → 几乎永不产出句子；
   - "完全新内容"分支（`SentenceSplitter.kt:80-83`）在保守模式**直接丢弃残留**。
   - → `commitSentence()` 整节课可能一次都不执行 → **`transcriptFile` 恒为 null**。
3. 精修通道补录路径写的是 `transcriptFile?.appendText(...)`（`RecorderService.kt:581`）—— **null 时静默跳过**，但 `emit("sentence_corrected", s)` 照常发出，UI 字幕照常显示 → **"字幕有、文件没有"**。
4. 叠加缺陷：补录路径**不更新 `lastCommitted`**（`RecorderService.kt:577-585`），此后每句精修都因 `prev == null` 或不匹配而反复走"补录"，永远走不到替换路径。
5. 直到停止时 `flushTranscript()`（`RecorderService.kt:280-287`）才首次创建文件；且 `flushRemaining()` 不分模式把无标点流式残句整段写入 —— HANDOVER 记载的"100 字流式垃圾 blob"**仍会出现在文件尾部**，与精修内容重复。

**修复方向**：

- 补录路径改为 `val f = transcriptFile ?: openTranscriptFile()`，与 `commitSentence` 对齐；
- 补录成功后更新 `lastCommitted = s; lastCommittedWasClosed = true`；
- `flushTranscript()` 在保守模式下不冲刷流式残留（尾巴按设计交精修通道，避免双份）。

### 2.2【中】退后台期间 UI 字幕断层（CaptionBuffer 设计自相矛盾）

**现象**：退后台再回前台，后台期间的句子在字幕区永久缺失（转录文件里完整存在），易被误判为"后台没识别/没落盘"。

**根因**：

- `CaptionBuffer` 注释自称"进程级缓冲，后台句子字幕不丢"（`CaptionBuffer.kt:3-7`），但其唯一写入入口是 `ListenFragment.sink`（`ListenFragment.kt:102-143`）；
- `ListenFragment.onPause()` 会摘除 sink（`ListenFragment.kt:86-89`）。App 按 Home → Activity/Fragment onPause → 后台期间所有 `sentence`/`sentence_corrected` 广播在 `MainActivity.kt:53` 空转 → CaptionBuffer 不更新；
- v0.10.2 修复的"切 tab 字幕不丢"只覆盖 show/hide（不触发 Fragment onPause），**未覆盖退后台场景**。

**修复方向**：CaptionBuffer 的更新挪到 `MainActivity.eventReceiver`（随进程存活），Fragment 的 sink 只负责触发渲染。这样"进程级缓冲"名实相符，退后台、Activity 重建均不断层。

## 4. 修复优先级建议

1. **P0 — §2.1 保守模式补录不落盘**：改动极小（补录路径 `?: openTranscriptFile()` + 更新 `lastCommitted` + `flushTranscript` 按模式区分），堵住"字幕有文件没有"的主漏。
2. **P1 — §2.2 CaptionBuffer 断层**：CaptionBuffer 更新挪到 Activity 层，Fragment 只渲染。
3. **P1 — §3-#1 停止丢尾**：finish 回调与 `running=false` 排序；停止前 `refineExecutor` 排队任务 await 一小段时间再 shutdown。
4. **P2 — §3-#2 DiagAsrReceiver 攻击面**：发布构建关闭导出。
5. **P2 — §3-#3/#4 健壮性与一致性**：模型目录完整性校验（失败即删目录重拷）；文件回写改 lastIndexOf 对齐 UI。
6. **P3 — 其余低级别项**随版本顺带清理。

### 6.2 第二轮要点展开

**#12（高）修复方向**（二选一）：
- 停止时在录音线程收尾处 `asrEngine?.release(); asrEngine = null`（与 mockEngine/systemEngine 的置 null 对齐），下次开始重新 init——代价是每次开始都重新加载模型（数秒）；
- 或给 `OfflineAsrEngine` 加"重置"能力（重建 stream + `running=true`），复用已加载模型——体验更好，但要处理 endpoint 后的 stream 生命周期。
- 同时建议：停止时 `refineEngine` 也一并释放置 null（它同样跨场次残留 VAD 内部状态）。

**#15（中）修复方向**：`RecordsFragment`/`ListenFragment` 重写 `onHiddenChanged(hidden)`，`hidden == false` 时 `reload()`/`refreshCourseHistory()`——与 show/hide 保活方案配套。

**#16（中）修复方向**：`AndroidManifest` 加 `android:fullBackupContent="@xml/backup_rules"` 排除 `classfox_prefs`；设置页 AI 配置处提示"建议使用 https 接口"。

### 6.3 优先级更新（合并第一、二轮）
