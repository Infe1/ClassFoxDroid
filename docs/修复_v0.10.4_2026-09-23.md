## 2. 高危修复详述

### F1（§2.1）保守模式：精修字幕整段静默不落盘

- **根因链**：保守模式下 `ingestAsrText` 不冲刷分句器残留（v0.10.3 刻意如此，防双份），全文由精修通道（SenseVoice 重转写）落盘；但 `applyRefined` 的补录分支写的是 `transcriptFile?.appendText(...)`——`transcriptFile` 只在流式 `commitSentence` 首次落盘时才惰性打开，保守模式下它恒为 null → 补录被 `?.` 静默吞掉，且 `lastCommitted` 不推进，后续替换匹配也找不到锚点。
- **修法**（`applyRefined` 补录分支，RecorderService.kt）：
  1. `transcriptFile ?: openTranscriptFile()` 兜底打开（文件头照常写）；
  2. 落盘后 `lastCommitted = s; lastCommittedWasClosed = true`——否则同一句的后续精修会再次走补录，写两遍；
  3. 补录前过一遍 `isNearDuplicate`，与流式路径行为对齐（替换漏配时不至于同句双份）。
- **配套**：`flushTranscript` 按模式区分——激进模式照旧冲刷残留，保守模式只写"结束"标记（冲刷会把无标点流式半句整段写进转录，与精修正文双份、时间戳乱序，即 v0.10.2 真机事故的另一半）。
- **验证**：保守模式真机/模拟器监听 2 分钟 → 转录文件应只有精修句（带标点、按音频时间），无流式半句、无重复句。
- **回退**：`git revert` 本 commit 中 `applyRefined`/`flushTranscript` 两处 hunk 即可，互不影响其他修复。

### F2（§6-#12）二次监听复用"死"离线引擎

- **根因链**：服务因 `BIND_AUTO_CREATE` 绑定存活，停止时不销毁；`OfflineAsrEngine.finish()` 后内部 `running=false` 不可逆，但 `asrEngine` 字段仍持有它 → 同一次 App 会话内"停止→开始"，`startOfflineEngine` 走"复用已就绪引擎"分支直接返回，`feedPcm` 全部空跑：整场无流式识别、无任何报错（精修引擎独立存活仍在出句，现象极具迷惑性）。
- **修法**（录音线程收尾处）：`asrEngine?.finish()` 之后 `release() + asrEngine = null`，与既有的 `mockEngine/systemEngine` 置 null 写法对齐。下一场 `startOfflineEngine` 重新初始化（模型文件已在 filesDir，秒级）。
- **配套**：`startRecording` 开头补 `refineEngine?.flushPending()`，清掉上一场残留在 VAD 缓冲里的尾音，避免污染新一场分段。
- **验证**：同一次 App 会话内 开始→停止→开始，第二场 logcat 应重新出现"离线ASR初始化中…已就绪"，字幕正常出。
- **回退**：单 hunk revert。

## 3. 中危修复详述

### F3（§2.2）退后台/切页字幕断层

- **根因**：`CaptionBuffer` 的写入挂在 `ListenFragment.sink` 里，而 sink 在 `onPause` 即注销（退后台、切 tab 都触发）→ 注销期间句子只落盘不进缓冲，回前台后少一段。
- **修法（职责上移，不改事件协议）**：`MainActivity.eventReceiver`（注册于 `onCreate`，退后台仍存活）先写 `CaptionBuffer`（partial/sentence/sentence_corrected 三个事件），再转发 `listenSink`；`ListenFragment.sink` 对应分支瘦身为只 `renderCaption()` + 记日志。匹配替换策略（orig 空追加、找不到跳过）原样保留在上移处。
- **已知边界**：若 Activity 被系统销毁而服务独存（极低内存），receiver 一并注销，缓冲仍会漏——进程级彻底解法是缓冲挪进 Service，属结构性改动，本次按"最小改动"原则不做。
- **验证**：监听中按 Home 键 1 分钟 → 回前台，字幕连续无缺段。

### F4（§3-#1）停止瞬间丢尾句/尾精修

- **根因**：`finish()` 的收尾文本 post 到主线程执行，而录音线程随即将 `running=false`——若主线程先看到 `running=false`，`ingestAsrText` 直接丢弃最后一句；同时 `stopSelf` 800ms 后 `onDestroy` 的 `shutdownNow` 可能打断还在跑的末段精修。
- **修法（三步，全部在既有结构上微调）**：
  1. 录音线程收尾的 `flushTranscript() + running.set(false)` 改为 `mainHandler.post { … }`——主线程 FIFO 保证 finish 冲刷出的最后一句先落盘，再写结束标记、再置停止位；
  2. 录音线程在收尾前 `refineExecutor.submit{}.get(2500ms)` 有界等精修排空（busy 位保证最多 1 段在跑，不会无限等）；
  3. `stopRecording` 的 `stopSelf` 延迟 800→2800ms（须大于上面的 2500ms 上限）。
- **验证**：讲话中按停止，最后一句话与末段精修都进转录文件，且结束标记在最后一行。

### F5（§6-#14）启动失败 UI 卡死

- **修法**：`ListenFragment.sink` 把 `"voice"` 与 `"error"` 拆开；`error` 分支 `isRunning=false; isPaused=false; render()`。服务侧启动失败路径（无权限/AudioRecord 初始化失败）本就发 `error` 广播但不发 `stopped`，UI 现在能复位，开始按钮重新可用。

### F6（§6-#15）show/hide 切回不刷新

- **修法**：v0.10.2 改 show/hide 保活后被 hide 的 Fragment 保持 RESUMED，`onResume` 不再触发。两个 Fragment 各补 `onHiddenChanged`：
  - ListenFragment：`!hidden` 时 `refreshCourseHistory() + renderCaption()`；
  - RecordsFragment：`hidden` 时 `stopPlayer()`（顺带修 §6-#23 播放中切 tab 不停），`!hidden` 时 `reload()`。

### F7（§6-#16）LLM Key 随备份外泄

- **修法**：新增 `res/xml/backup_rules.xml`（≤Android 11）与 `res/xml/data_extraction_rules.xml`（Android 12+，云备份+设备迁移），均排除 `sharedpref/classfox_prefs.xml`；Manifest 挂两个属性。`usesCleartextTraffic` 保留（自建 LLM 端点可能 http），建议服务端上 https。

### F8（§3-#2）DiagAsrReceiver 输出路径收敛

- **修法**：receiver 保持 exported（真机调参流程依赖 adb 广播，改非导出会破坏工作流），但 `out` 参数限定必须位于应用私有目录内（`canonicalPath` 前缀比较，带分隔符防前缀攻击），越界直接拒绝。输入 wav 路径不限制（MuMu 调参需读 /sdcard，且读出内容只能写回应用目录，泄露面已封死）。

## 5. 接口/行为变化说明（交接要点）

1. **事件协议不变**：广播 kind 集合不变；语义变化仅两处——`sentence` 现在关键词命中时也会发（以前只在未命中时发）；final 帧不再伴随 `partial`。
2. **CaptionBuffer 写入责任方**：`MainActivity.eventReceiver`（Activity 存活期全程）。Fragment 的 sink 只负责渲染。新加 UI 页要显示字幕时，只读 `CaptionBuffer` 渲染即可，不要再各自写缓冲。
3. **引擎生命周期**：`asrEngine` 在录音线程收尾即 release+null——任何"监听中"之外持有 `asrEngine` 引用的代码都不允许存在（目前只有 startOfflineEngine 初始化线程，已有 running 检查）。
4. **保守模式落盘唯一入口**：`applyRefined` 补录分支（精修通道）。精修不可用时保守模式无落盘，属预期。
5. **构建**：`versionCode 20 / 0.10.4`；新增两个 res/xml 备份规则文件，勿删。
